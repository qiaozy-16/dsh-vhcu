## 1. 插件入口与 `apply()` 生命周期

### 1.1 入口导出【码】

| 项 | 值 | 位置 |
|---|---|---|
| `export const name` | `'dsh-vhcu'` | `lib/index.js:66` |
| `export const inject` | `['webServer', 'tools']`（两服务硬依赖） | `lib/index.js:67` |
| `export function apply(ctx)` | 唯一挂载入口 | `lib/index.js:158` |
| 返回值 | `{ snapshot, start, stop, dispose }` | `lib/index.js:5719-5724` |

`dsh.plugin.json:14-20` 与 `package.json:35-44` 的 entry/inject 与代码一致；bundle 通过 `cordis.patch.yml:10-12` 的 `insert` 行挂进 profile（不覆盖、不禁用任何核心行）。

### 1.2 `apply()` 初始化顺序（按执行序）【码】

1. `safeLogger(ctx)`：`ctx.logger` 逐方法包裹 try/catch，日志永不拖垮插件（`104-121`、`159`）。
2. `resolveRuntimePaths({root})` 解析 5 条绝对路径（`163`）；随后做**一次性兼容迁移**：用清空 `DSH_PROFILE*` 的 env 再解析一次 legacy 路径，仅当新路径不存在且旧路径存在时，复制 `settings`/`macros`，**不迁移 `session_state`**（`167-182`）。
3. 实例化 `SettingsStore` / `SessionStateStore`（`183-184`）；`let settings = settingsStore.settings`（`261`）。
4. 注册 `tools/execute` 中间件（脚本写入拦截，`189-196`）。
5. 初始化 `state`（phase/counters/hear/privacy/interaction/approval/macroQueue/recording…，`204-258`）。
6. 启动 `settings.json` **目录 watch**（`{persistent:false}`，原子替换会换 inode 故监听目录），回调里 `refresh()` + `pushStatus()`；用 `ctx.effect` 归还 close（`266-285`）。
7. `setRecoveryFromStore()`：若上次队列用了图片坐标则**直接丢弃**（跨重启不可安全恢复），否则生成 recovery 摘要（`287-323`）。
8. 内存态资源：`frameSecret = randomBytes(32)`（`528`）、元素缓存（`390-438`）、SSE `clients`/`ring(200)`（`440-441`）、fusion（`456-484`）。
9. `MacroStore` 构建失败只记 error，`macroStore=null`（`373-378`）——之后所有宏工具返回 `E_UNAVAILABLE`（`4031`、`5141`、`5225`）。
10. `attachSupervisor` 只在首次 `ensureSupervisor()` 时调用（`1057-1074`），**apply 阶段绝不 spawn Python**（文件头约定 `15-18`）。
11. 注册 11 条路由（含 2026-11-28 新增的 `/vhcu/attachments`），再注册 28 个工具。
12. 注册生命周期清理：`ctx.effect(() => cleanup, 'vhcu: lifecycle')`（`5700-5705`）+ `ctx.on('dispose', cleanup)`（`5707`）——**双通道**。
13. `syncRuntimeGuards()`（`5708`）、启动时 `cleanupWorkspaceArtifacts({minAgeMs:60000})`（`5709-5716`）、最后打一行 mounted 日志（`5717`）。

### 1.3 失败边界（升级时最容易被忽略的一层）【码】

- `apply()` 内部**任何未捕获异常都会中止整个 apply**，而 Cordis 的语义是"apply 中止即卸载该插件全部注册项"。源码注释明确写了这条教训：profile 身份只从宿主环境变量取，**绝不在 apply 里探测 ctx 服务**，因为"Cordis accessor 在服务缺席时会抛，apply 中止会卸载全部 28 个工具"（`160-162`）。
- 该边界有回归测试：`host/test/plugin.test.mjs:1778-1802`（A1：把 `ctx.profile`/`ctx.app` 的 getter 改成 throw，断言 `apply` 不抛且 `tools.size === 28`）【测】。
- 但**注册层是分级吞异常的**：
  - 路由注册无 try/catch，`webServer.register` 抛错 → 冒泡 → 整个 apply 中止（`1755-1762`）。
  - 工具注册**逐个 try/catch，只 `logger.error`**（`5531-5533`）→ 抛错时插件"挂载成功但少了工具"，只剩一行 error 日志，属于**静默降级**。

## 3. HTTP 路由（11 条，全部 `kind:'exact'`）

通用约束【码】：`sameOrigin(req)` 比较 `Origin.host === headers.host`，**缺失 Origin 视为同源**（`133-142`）；POST 一律要求 `x-vhcu: 1`（除 `/vhcu/frame`）；JSON 体上限 8192 B，超限抛 `E_PROTO`（`144-156`）；所有响应 `cache-control: no-store`（`123-131`）。

### 3.1 帧 URL 签名【码】

`frameUrl()` 构造 payload `"x|y|w|h|exp[|seq]"`，HMAC-SHA256（每进程随机 `frameSecret`），TTL 5 分钟（`FRAME_TTL_MS=5*60*1000`，`83`）；`maxw` 夹在 `64..16384`——注释说明高精度截图会传物理宽度，渲染端不得再压回 1920（`551-553`）。校验用 `timingSafeEqual`（`563-572`）。

### 4.2 输出 renderer 机制【码】

- 通用 `TOOL_OUTPUT`：`schema: {type:'object', additionalProperties:true}`，`render` → `describeToolResult()`。
- **图片传输双轨**（2026-11-28，最终形态）：`url` 轨在 Markdown 里给签名链接；`attachment` 轨把 PNG
  交给宿主附件服务（`ctx.get('attachments').saveImage({data, mediaType})`）拿到 ref，renderer 返回
  `[{type:'text'}, {type:'image', attachment:ref}]`——与 `dsh-vision-router`（core-primitives.js:337-363）
  和 MCP 适配层（dsh-mcp-client/lib/index.js:343）同形。`vhcu_get_full_frame` 与 `vhcu_capture_target`
  用 `FRAME_OUTPUT`；`vhcu_get_vision_events` 用 `EVENTS_OUTPUT`（每次最多 3 张 ROI 图）。
  四级兜底：无 attachments 服务 / 非 PNG / `saveImage` 抛错 / 模型路由明确无 image 输入 →
  回退 URL 并带 `payload_mode_downgraded:true` + `payload_hint`，截图永不丢。
  能力无法确认（未知）时按"照试"处理。**base64 文本内联已废弃**：宿主把它当文本截断，模型看不到图。
  纯函数在 `host/lib/payload.js`，测试在 `host/test/payload.test.mjs`。

- **附件预算与专属回收**（2026-11-28）：宿主 `AttachmentStore` 没有 delete/list API，且其 README
  明确"永远不会自动删除"；会话历史是 zstd 压缩的，无法可靠枚举引用。所以 VHCU **只删自己写过的**：
  `host/lib/attachment-registry.js` 维护持久台账（`attachments_registry.json`：id/字节/时间，原子写，
  损坏自动隔离），双限 **2000 张 或 500 MiB**，超限即停止生成并静默回退 URL（`payload_mode_downgraded`）。
  `host/lib/attachment-gc.js` 只从台账取最旧条目、校验 64 位 hex、拼 `objects/<2>/<sha256>`，
  **经 `host/lib/trash.js` 移入系统回收站**（Electron `shell.trashItem` → Windows
  `SendToRecycleBin` 兜底；两条都不可用时抛 `E_TRASH_UNAVAILABLE`，**绝不 `unlink`**）。
  `POST /vhcu/attachments {action:'cleanup', keep_count?}` 默认保留最近 200 张；
  UI 显示 `附件 n/2000 · x/500 MB`，配额将满/已满时变红并给一键清理按钮。
- 专用 renderer 4 个：`CLIPBOARD_OUTPUT`（成功时回原文，`1776-1784`）、`find_elements`（带 `output.schema` 要求 `elements[].element_id`，`4223-4243`）、hear events（`5339-5342`）、multimodal events（`5374-5377`）。
- `render` 里拼接的**屏幕/转写文本一律经过 `wrapUntrusted()`**：包进 `<untrusted_screen_data>` 并把内部 `<`/`>` 转义为实体，防止闭合外层注入（`1804-1816`）。这是提示注入防线，不是可选项。
- 失败结果渲染会额外给出图片/队列明细（`1858-1867`、`2044-2061`），因此错误路径也能看到 `frame_url`。

### 4.3 工具生命周期事件【码】

- `beginTool(name)` 生成 `{name, callId:'vhcu-<n>', startedAt}`（`5450-5456`），`endTool` 补 `{ok, code, durationMs}`（`5458-5465`）。
- 注册时**包裹 `execute`**：进入前 `broadcastToolStart`，返回/抛错后 `broadcastToolEnd`，最终 `ctx.emit('vhcu/tool_start'|'vhcu/tool_end', payload)`（`5494-5530`、`5475-5491`）。
- 事件载荷**只含 name/callId/ok/code/durationMs**，刻意不含工具参数与结果（`5444-5448` 注释；测试 `plugin.test.mjs:1638`）【测】。
- 描述前缀注入：所有工具描述前置"优先使用 VHCU、E_PRIVACY_BLOCKED 时禁止外部兜底"等段落（`5395-5442`），`vhcu_start_vision` 额外加坐标/兜底/闭环三段，视觉动作类工具加"拿不准先重新取图"段（`5437-5439`）。

## 7. 持久化

### 7.1 路径解析（`host/lib/paths.js`）【码】

- 数据根：`%LOCALAPPDATA%` → `XDG_DATA_HOME` → `~/.local/share`（`26-28`）。
- 状态目录：`<data>/dsh-vhcu`；若存在 profile token 则为 `<data>/dsh-vhcu/profiles/<sha256(raw).slice(0,16)>`（`30-38`、`55`）。
- profile token 取自 `DSH_PROFILE_KEY || DSH_PROFILE || DSH_PROFILE_DIR`（`30-33`）——**取原始字符串做哈希，不拼进路径**，`../x` 这类值也无害（注释 `35-36`）。
- 5 条产出：`models`（默认 `<repo>/models`）、`macros`、`logs`、`settings`、`sessionState`；`VHCU_*_PATH` 覆盖值必须是绝对路径，否则 `E_CONFIG`（`14-24`、`56-72`）。`models/logs` 保持全局共享，只有用户状态按 profile 隔离（注释 `53-54`）。

### 7.2 settings.json（`host/lib/settings.js`）【码】

- 读取：兼容 `{version,settings}` 与裸对象；损坏时**先 `rename` 成 `.broken`** 再用默认值重建，并记录 `lastError`，绝不静默（`188-226`）。
- 写入：`temp + rename` 原子替换、`mode 0o600`；失败抛 `E_SETTINGS_PERSIST` 并清理 temp（`294-314`）。路由层**先落盘再改内存**，不假装成功（注释 `1474-1475`）。
- 跨窗口：`refresh()` 用 `mtimeMs + size` 双重判断，变化才重读；`update()` 先 `refresh()` 再 diff 出真正变化的 key，避免旧窗口覆盖别人的新值（`239-292`）。目录 watch 与 `/vhcu/settings` GET 都会触发 refresh（`268-274`、`1458-1459`）。
- 校验：枚举白/黑名单、`uiaDefaultDepth 1..10`、`retryMaxAttempts 0..5`、黑名单去重且 ≤50 条/64 字（`48-174`）。

### 7.3 macros.json（`host/lib/macros.js`）【码】

- 上限：**100 个宏 / 100 步 / 40 个分类**（`24-25`、`62`），名称 `2-64` 且限字符集（`335-341`），描述 240、文本 2000（`27`、`39`）。
- 内置宏：`seedMacros()` 18 个（含 `macro_launch_app`、`macro_close_active_window`(is_destructive)…`262`）；加载时**代码拥有内置定义**，逐字段比对后升级旧持久化版本，但保留用户的 enabled 选择（`554-590`）。
- 只读保护：内置宏不可 `update`/`remove`（`681-683`、`704-706`），内置分类不可删除（`651-653`），错误码 `E_DENIED`。
- 迁移：legacy `open_notepad_and_type`/`macro_create_vhcu_folder` 折叠掉（`517-521`）；空 `global` 分类清理（`592-596`）；超过 100 步的旧宏**截断而非判损坏**（`481-483`）。
- 持久化：`temp + rename`（`713-722`），失败不吞（`add` 里直接向上抛）。

### 7.4 session_state.json（`host/lib/session-state.js`）【码】

- 单所有者：Node 拥有队列状态，Python 一次只跑一个宏，因此恢复粒度是**宏级 at-least-once，不是步级**（注释 `3-7`）。
- 校验：`version===1`、`queue_id ~ ^q_[a-z0-9]{8,64}$`、status 白名单、`total 1..20`、`index<=total`、`items.length===total`、`updated_at` 不超过 24 h（`35-87`、`25`）。
- 写入：`open + write + (可选 fsync) + rename`；**fsync 由 `VHCU_STATE_FSYNC==='1'` 控制**（默认关，避免队列延迟被磁盘绑死，注释 `138-141`；`index.js:2094`）。
- 损坏：`_quarantine()` 改名 `.broken`，绝不让坏文件阻塞启动（`174-181`）；测试 `session-state.test.mjs:67`【测】。
- 恢复流：`setRecoveryFromStore()` 在 apply 时读（`302-323`）；图片坐标队列**永久丢弃**（`308-319`、`3567-3574`）；`resumeRecovery` 先确保视觉在跑再重放（`3575-3598`）；`discardRecovery`（`3601-3609`）。

## 10. 对 0.2.2 升级最敏感的 5 个点

1. **`ctx.tools.register(definition)` + `output{schema,render}` 契约，且失败是静默的。**
   风险不在"抛错"，而在"少注册"：`registerTools` 逐个 try/catch 只打日志（`index.js:5531-5533`），任何 definition 字段不合法都只表现为"模型看不到某个工具"。若 0.2.2 收紧 `parameters` 必须是 TypeBox/JSON-Schema 子集、或要求 `output` 具备别的形状，28 个工具可能部分消失而无硬错误。生态里已存在 `tools.register` / `tools.registerTool` 两种名字的探测（`dsh-vision-router/lib/dsh-host-capabilities.js`），提示方法名并非绝对稳定——但**这不能证明 0.2.2 改名**，需实机核验。

2. **`ctx.webServer.register({kind:'exact', path, handler})` 与 origin 解析。**
   路由注册**没有 try/catch**（`1755-1762`），一旦形状变化就是 apply 中止 → 连带 28 个工具一起被卸载（第 1.3 节的边界）。同时签名 URL 是绝对地址，依赖 `getOrigin()/origin/port` 三级回退（`530-540`）；三者都没有时 `frame_url` 变相对路径，图片在面板里可能仍能显示，但模型侧 Markdown 链接会失效。此外若 `register` 返回 `void`，`disposers` 退化为 no-op，热重载时路由会残留（`1758`）。

3. **`ctx.on('tools/execute', (exec, next))` 中间件与拒绝返回值形状。**
   这是"禁止模型用 shell 截图到工作区"的唯一入口（`189-196`）。0.2.2 若改中间件签名/改为异步裁决/改 `exec` 字段名（`name`/`args`），拦截会静默失效——安全防线退化但功能全正常，属于最难发现的一类回归。注意 `typeof ctx.on !== 'function'` 时整段被跳过（`189`），本身就是一个静默降级点。

4. **`ctx.effect` / `ctx.on('dispose')` 双通道清理语义。**
   `cleanup()` 是唯一负责"不留子进程、不留定时器"的地方（`5673-5698`），同时挂了 effect 与 dispose 两条通道。0.2.2 若改变 effect 的 dispose 时机（或热重载更频繁），可能出现：SSE interval 残留、`uiohook` 全局钩子未卸、Python 子进程成为孤儿。后者的兜底只有 `process.once('exit')` 里的同步 `taskkill`（`supervisor.js:292-311`）——只覆盖"宿主进程整体退出"，不覆盖"插件单独卸载/重载"。

5. **升级入口本身：清单版本门 + `DSH_PROFILE*` 路径假设。**
   - 版本门：`package.json:20` 的 `engines.dsh` 是 `>=0.1.5-rc.1 <0.3.0-0`（允许 0.2.2），但 `dsh.plugin.json:8-12` 的 `compatibility.dshReleases` 只列到 `0.2.1-rc.3`。仓内**没有任何代码读取 `dshReleases`**（全仓 grep 仅命中清单本身与发布检查表），所以它是否被 0.2.2 的 plugin-manager/市场读取是未知项；若它参与门禁，0.2.2-rc5 会被判不兼容。
   - 路径：`paths.js` 的 profile 隔离完全依赖 `DSH_PROFILE_KEY`/`DSH_PROFILE`/`DSH_PROFILE_DIR` 三者之一（`30-33`）。本机其它插件（`dsh-unified-agent-memory/lib/utils.js:74`）也在读 `DSH_PROFILE`，说明这是生态共识；但**无法从本会话证明 0.2.2 仍会注入**（本会话 shell 环境看不到任何 `DSH_*` 变量，可能被过滤）。若不再注入：profile 隔离静默失效，所有 profile 共用 `<data>/dsh-vhcu`，且 `apply` 里的 legacy 兼容复制（`167-182`）会把旧 settings/macros 当成"新路径为空"再复制一次——不致命，但会让"每个 profile 独立状态"这一宣称不成立。
