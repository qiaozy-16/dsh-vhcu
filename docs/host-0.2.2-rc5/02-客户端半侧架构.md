# 02 · dsh-vhcu 客户端半侧架构（对照 host 0.2.2-rc.5）

> 调研员：arch-client · 任务 task-2 · 只读调研，未修改任何源码、未安装/升级 DSH。
> 证据分级：**[源码]** = 实读 `dsh-vhcu` 仓库；**[0.2.1包]** = 实读本机已装宿主包/`node_modules`；
> **[0.2.2包]** = 实读 `.tmp/hostdiff/x022` 中解包的 0.2.2-rc.5 npm 产物；**[推断]** = 由以上证据推出的结论。

## 0. 一句话结论

dsh-vhcu 的客户端是**单文件、无构建、手工 CJS 自描述模块**；它对宿主的硬依赖只有四个：
`window.__ModuleLoader__.load(...)`、`require('react')` 平台 seed、Cordis 的 `ctx.betterSidebar`/`ctx.effect`、
以及同源 `/vhcu/*` 路由。它**完全不使用**宿主 slot API、主题、语言、会话、尺寸接口；
面板的 tab 宿主能力全部来自第三方 `dsh-better-sidebar@0.28.0`。因此 0.2.2 的客户端风险主要是**间接的**：
宿主 → betterSidebar → vhcu 的传导链，而不是 vhcu 直接调用的核心 API。

## 1. 模块装载方式

### 1.1 自描述模块格式

`lib/client.js:12-14`：

```js
window.__ModuleLoader__.load({
  id: 'dsh-vhcu',
  factory: (require) => { ... return module.exports; },
});
```

- 脚本执行时**只注册 factory**，模块体（含 CSS 注入）都在 factory 闭包内，首次 import/require 时才物化。这是 0.2.x 一致的“惰性 CJS 表”模型：**[0.2.2包]** `@deepseek-ai/dsh-client-modules` 的 `lib/types/client/manifest.d.ts:9-16` 明确写明“执行插件 bundle 只注册 factory”。
- 注册形状 0.2.2 **未变**：`ClientBundleRegistration { id; chunk?; factory }`（同文件 `:200-212`）；`id` 是包名，`/client` 后缀会被 `stripClientSuffix` 归一（`:162-171`）。
- 0.2.2 新增了 `require.asset(reference)`（`:187-199`，对应 `ClientModuleCreateOptions.resolveAsset` `:214-223`）。vhcu 的 factory 只 `require('react')`，**新增能力不影响它**。
- 0.2.2 的引导 façade 仍是同一段 HTML 头脚本：`window.__ModuleLoader__={mode:"queue",pendingQueue,load(registration){...},create(options){...}}`（**[0.2.2包]** `lib/index.js:521-545`）。
  即无论 vhcu 的脚本在 `create()` 之前执行（入 `pendingQueue`）还是之后执行（`mode` 已切到 `live`，直接注册），`load({id,factory})` 都是同一入口。

### 1.2 require('react') 来自宿主运行时

`lib/client.js:16-18`：

```js
const React = require('react');
const h = React.createElement;
const { useCallback, useEffect, useRef, useState } = React;
```

`require` 是宿主模块表的同步解析器，解析顺序为“平台 seed 表 → 已物化记录 → 启动图 row → 已注册 factory，否则抛错”（**[0.2.2包]** `manifest.d.ts:18-24`）。
`react` 属于**平台 seed（platform singleton）**，不是 npm 依赖：`package.json` 的依赖里没有 react（`package.json:1-45`），
也不在 `dsh.client.inject` 里（`:42` 为空数组）。0.2.2 的类型契约未改 seed 机制，但**未拿到 0.2.2 shell 的 seed 表原文**（见 §8 未验证项）。

### 1.3 为什么没有构建步骤

- `package.json:8` `main` 指向宿主半侧 `./lib/index.js`；`:14` `exports["./client"] = "./lib/client.js"` 直接暴露手写文件；`dist/`、`build/` 只放 Python daemon 产物（实读 `ls dist build`）。
- `scripts/*.mjs` 中没有任何引用 `lib/client.js` 的打包/转译逻辑（`grep client.js scripts/*.mjs` 无匹配）。
- 代码是 `React.createElement` 直写（79 行含 hooks，无 JSX），因此浏览器可直接执行，不需要 swc/vite 产物。
- 这也是 0.2.2 升级的“好消息”：没有构建链需要跟随宿主更新，但也意味着**没有类型检查**兜底（见 §7）。

### 1.4 package.json 的 dsh.client 与 dsh.plugin.json 的分工

| 文件 | 字段 | 值 | 消费方与语义 |
| --- | --- | --- | --- |

## 2. 插件注册与 betterSidebar 契约

### 2.1 注册调用

`lib/client.js:2649-2668`：

```js
const name = 'dsh-vhcu';
const inject = ['betterSidebar'];
function apply(ctx) {
  const sidebar = ctx.betterSidebar;
  if (!sidebar || typeof sidebar.registerTab !== 'function') return;   // 2654-2656 静默 no-op
  const register = () => sidebar.registerTab({
    id: 'vhcu:monitor', title: 'VHCU',
    description: '视觉/动作/听觉三栏监控、设置与实时事件流',
    order: 120, single: true,
    component: (props) => h(Panel, props),
  });
  if (typeof ctx.effect === 'function') ctx.effect(register, 'vhcu: sidebar tab'); // 2666
  else register();                                                                  // 2667
}
```

- **只注册一个 tab**：`id='vhcu:monitor'`、标题 `VHCU`、`order=120`（默认 100，故排在多数内置项之后）、`single=true`（同类型只开一个实例）。
- **没有注册 `icon`**：`client.test.mjs:78` 专门断言 `descriptor.icon === undefined`；插件列表图标来自 `package.json:5` / `dsh.plugin.json:5` 的 `assets/icon.png`，不走侧边栏 descriptor（`client.test.mjs:293-306`）。
- **清理**：`registerTab` 返回 disposer（**[0.2.1包]** `dsh-better-sidebar/lib/types/client/service.d.ts:599-604`，文档说“cordis auto-invokes on fiber disposal”），再用 `ctx.effect(register, ...)` 包一层；`dev/mock-ctx.mjs:58-66` 的 `effect` 会把返回的 disposer 存起来并在 dispose 时调用（`:75-92`）。
- **失败姿态**：`ctx.betterSidebar` 缺失或方法改名时不是抛错，而是**静默 return**。这一点会与 0.2.2 的新失败可见性相互作用（§5、§8）。

### 2.2 dsh-better-sidebar 0.28.0 的依赖点逐个列

| vhcu 依赖点 | 位置 | betterSidebar 契约 |
| --- | --- | --- |
| 服务名 `ctx.betterSidebar` | `lib/client.js:2653` | `lib/client.js:31961` `ctx.provide("betterSidebar", service)`；类型 `service.d.ts:599-604` |
| `registerTab(descriptor)` 存在且返回 disposer | `lib/client.js:2654,2658` | `service.d.ts:603` |
| `id` | `:2659` | `TabDescriptor.id`（`service.d.ts:146-148`），同时作为 `SidebarTab.type` |
| `title: 'VHCU'` | `:2660` | `:149`，支持 string / () => string |
| `description` | `:2661` | `:150-160`（宿主新标签页引导最多列 4 条时显示） |
| `order: 120` | `:2662` | `:162-163`，升序，默认 100 |
| `single: true` | `:2663` | `:187-193`，等价 `dedupeKey: () => id` |
| `component: (props) => ...` | `:2664` | `:272`，props 类型 `TabComponentProps`（`:127-144`：ctx/store/scope/tab/**visible**/…） |
| `ctx.effect(body,label)` | `:2666` | 宿主 Cordis API（非 betterSidebar 专属） |

**vhcu 对 `TabComponentProps` 的使用率为 0**：`Panel({ initialTab='vision' })`（`lib/client.js:1477`）只读 `initialTab`，
`ctx/store/scope/tab/visible` 全部忽略；`grep "visible" lib/client.js` 无命中。因此 betterSidebar 的 props 契约变化对**渲染**影响很小，
但也意味着面板不会因 `visible=false` 暂停轮询/SSE（见 §4.4）。

- 所有**写操作**都带 `content-type: application/json` + `x-vhcu: 1`；宿主每个写路由都校验这两个头与 `sameOrigin`（`lib/index.js:133-142`、各路由内）。
- SSR/页面路径是写死的根路径 `/vhcu`（`lib/client.js:20`），不做 base-path 拼接。
- 客户端**未使用**的宿主能力：`/vhcu/control` 的 `restart`/`ping`/`hear.status`、`GET /vhcu/recovery`、任意 `/vhcu/frame` 的 `maxw` 覆盖。
- `fetch` 全部没有 `AbortController`/超时；只有 `EventSource` 自带重连（`onerror → link='retry'`，`1633`）。
- 宿主 SSE 客户端上限 `MAX_CLIENTS = 4`（`lib/index.js:73`），超限 429（`:1631`）。客户端每个 Panel 实例各开一条 SSE（`1627`），关闭仅在 unmount（`1683-1687`）。

### 4.2 SSE 帧语义

- `hello`：`{state, events}` 快照（`lib/index.js:1643-1648`）；客户端 `applyPayload` 处理（`1634-1641`）。
- `status`：**整份 `snapshot()`**（`:727-730`）；客户端直接 `setState(payload)`（`1645`）——是覆盖而非 merge。若存在本地乐观更新（如 `approval:null`，`:1748`），随后到达的旧 status 可能把它覆盖回来（窗口极小，属既有行为）。
- `event`：仅四类数据事件会作为 `event` 推送；内部 note 只进 ring 不推流（宿主 `:625-638`，注释 `:629-630`）。
- Hear 文本事件到达时客户端会**强制**把 `hear.state` 置为 `listening`（`:1662-1672`），弥补丢帧。
- gear 打开时，status 里 `macrosRevision` 变化会触发 `fetchMacros()`（`:1647-1652`，ref 在 `1560`）。

### 4.3 宿主 snapshot 字段 → 客户端消费点

`snapshot()`（`lib/index.js:576-590`）= `state`(204-258) + `clients/lastEventId/elementCacheSize/recent/settings/macrosRevision`。
客户端消费位置：`phase`(1947)、`hear`(1949-1985)、`recovery`(2395-2428)、`approval`(2436-2478)、`macroQueue`(2429-2435)、
`privacy`(2533)、`interaction`(2563-2567)、`lastError`(2568-2570)、`cursorWarning`(2571-2573)、`precision`(2574-2580)、
`macroGenerationNotice`(2581-2587)、`recording`(2217)、`settings`(1600/1646)、`macrosRevision`(1649)；`recent` 未用（列表走 `events`）。
2026-11-28 新增 `paths: {profileScope, stateDir}`（仅用于诊断 profile 隔离是否生效，客户端暂未消费）。

### 4.4 生命周期缺口（既有事实，非 0.2.2 引入）

- Panel 不用 `visible`：tab 隐藏但组件仍 mounted 时，SSE 与 200 条事件状态继续存活。
- betterSidebar 支持 `keepMounted`/多会话并存（**[0.2.1包]** `service.d.ts:250-253, 585-592`），
  多会话各开一个 `vhcu:monitor`（`single` 只在同一会话内去重——[推断]，去重键 `() => id` 存于会话 store），就会各自 `new EventSource`。
  叠加宿主 4 客户端上限，第 5 个会话/窗口起会得到 429，面板 footer 显示 `SSE retry`（`:2623`）而不是显式“连接被拒”。

### 5.2 保存与“分叉/refresh”机制

- **全量 draft 提交**：`saveSettings` 把整个 `draft` POST 上去（`1716-1720`），宿主 `settingsStore.update` 落盘后再 `pushStatus()`（`lib/index.js:1476-1493`）；保存成功即 `setSettings(payload.settings)` 并关闭弹层（`1722-1724`）。
- **宿主侧 merge 白名单**：`mergeSettings`（`host/lib/settings.js:112-176`）逐键校验，未知键忽略。因此客户端 placeholder draft 里多出的 `macros.open_notepad/save`（`1514`）只会命中有白名单的这两个键。
- **草稿不被 SSE 覆盖**：`SettingsPanel` 内 `isDirty` 为真时不接受新的 `settings` prop（`535-539`）；`patch()` 置 dirty（`540-543`）。代价是：另一窗口改了设置后，本窗口弹层里仍是旧草稿，保存时**整份覆盖**（last-write-wins，无冲突检测）。
- **客户端 placeholder 默认值与宿主默认值不一致**：初始 settings（`~1478-1515`）缺 `allowHighPrecisionVision` 与 `enableMacroAutoGeneration`，且 `macros` 是旧字段。（2026-11-28 已补 `visionPayloadMode: 'url'` 的 placeholder；其余两项仍未补。）若 `GET /vhcu/settings` 失败（`1625` 的 catch 静默吞掉），UI 会以 `allowHighPrecisionVision !== false → 勾选`（`983`）呈现“开启”，而宿主实际值未知；此时点保存会把 placeholder 值写回。**这是真实的设置分叉点**（[源码] 事实 + [推断] 触发条件）。
- **跨窗口刷新**：宿主对 settings 目录 `fs.watch`（`lib/index.js:263-285`），原子写换 inode 也能捕获；变更后 `settingsStore.refresh()` + `pushStatus()`，所有打开的面板收到 status 里的新 `settings`。GET `/vhcu/settings` 也会强制 refresh（`:1457-1459`）。宏没有文件监听，仅靠 `macrosRevision`（snapshot `:588`）在 gear 打开时懒刷新。
- **持久化信息未展示**：宿主在 GET/POST 里返回 `persistence:{path,revision,error}`（`:1460-1468`、`:1494-1502`），客户端完全忽略；落盘失败只能表现为 POST 非 200 的 `error`。

## 8. 0.2.2 升级风险：精确断点

## 9. 对 0.2.2 升级最敏感的 5 个点

1. **`window.__ModuleLoader__.load` 全局契约**（`lib/client.js:12-14`）。
   0.2.2-rc.5 仍是 `{id, factory}` 且 façade 代码可读（[0.2.2包] `client-modules/lib/index.js:521-545`、`manifest.d.ts:200-212`），
   这是一切的前提；一旦宿主改注册入口或 id 归一，vhcu 是“零日志消失”。

2. **`require('react')` 平台 seed**（`:16-18`）。
   没有任何构建/类型检查兜底；测试里的 react 是自写 stub（`client.test.mjs:38-47`），
   宿主 seed 表若变化，现有测试**发现不了**，只会在真机物化时抛错。

3. **`ctx.betterSidebar` + `registerTab` 形状**（`:2650, 2653-2666`）。
   这是唯一的面板宿主接口，且失败被 `return` 吞掉（`:2654-2656`）。
   0.2.2 核心 sidebar slots 已有新增（`slots.d.ts:20,86,118`），传导链是
   宿主 → `dsh-better-sidebar@0.28.0` → vhcu；若 betterSidebar 被迫升级，`TabDescriptor` 字段/`component` props 都可能变。

4. **客户端条目启动失败可见性变了**（0.2.2 `entries.ts:97` + `:255`）。
   0.2.1 一个坏模块会中断 startup；0.2.2 变成“记日志 + inactive + reconcile failure”。
   对 vhcu 而言，注册失败从“启动即炸”变成“面板悄悄没了”，**更难定位**；
   需要用 `client-modules: dsh-vhcu is waiting for activation` 这类 failure 反查，而不是看 vhcu 日志。

5. **SSE 连接预算 × 面板生命周期**（客户端 `:1627, 1683-1687`；宿主 `:73`）。
   面板不用 `visible`、每实例一条 EventSource，而 betterSidebar 支持多会话 keepMounted（`service.d.ts:250-253, 585-592`）；
   4 客户端上限会在大开 tab/多窗场景下先于 0.2.2 任何 API 变更爆掉，升级验证时必须一并测。

## 10. 已确认的“升级不敏感”项（减少无效排查）
