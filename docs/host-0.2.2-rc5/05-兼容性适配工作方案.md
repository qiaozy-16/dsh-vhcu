## 1. 目标与非目标

### 目标
1. 让 dsh-vhcu v1.1 在 **0.2.1-rc.3（当前）** 与 **0.2.2-rc.5（升级后）** 上都能正常挂载、注册 28 个工具、10 条路由、侧栏面板与宏/设置状态。
2. 借升级窗口修掉调研中确认的**既有缺陷**（脚本写入拦截从未生效），并补齐对应测试。
3. 形成可复用的升级自检清单与回滚步骤，降低用户手动升级的试错成本。
4. 输出：代码改动（最小面）、测试、基线/升级报告、版本与文档更新。

### 非目标
- 不做 V1.2 的架构重构（PointerManager / ActionScheduler / Perception / 工具分层）。
- 不替代用户执行宿主升级；不修改 `D:\deepseek-harness` 安装目录。
- 不新增工具、不改 28 个工具名 / 参数 schema / 返回码 / 宏格式。
- 不支持 PTC executor 模式（VHCU 是 native 工具集；只要用户不切 PTC 即无影响）。
- 不在本轮处理 macOS/Linux 引擎或 V1.2 能力。

## 2. 兼容策略

| 策略 | 做法 |
|---|---|
| **双宿主兼容** | 用能力探测与字段回退（`exec?.arguments ?? exec?.args`、可选 API 判空），不按版本号硬分支；改完后必须先在 0.2.1 上全量回归 |
| **最小侵入** | 只动“宿主契约已变 / 已错”的点；28 工具定义、路由、renderer、宏/设置格式保持字节级不变 |
| **失败可观测** | 不新增静默 `catch`；新增/修改路径要有结构化日志或状态字段，便于升级后定位 |
| **不碰运行中的宿主** | 0.2.2 验证用 `.tmp/` 解包副本 + 独立 user-data；真实升级由用户执行，我们只做升级前备份与升级后 smoke |

| **每轮留痕** | 工作区根目录写带时间戳 `.txt` 工作日志；本目录 `.md` 记录结论与证据 |

### 阶段 3：0.2.2 隔离验证（需用户批准“解包不安装”，约 0.5～1 天）
1. **取出 0.2.2 的 app.asar**：安装包是 NSIS/LZMA，本机无 7z。方案：下载便携 `7zr.exe` 到 `.tmp/`（不安装），或让用户提供已安装的 0.2.2 `resources/app.asar`；只读解包到 `.tmp/hostdiff/asar022/`，核对 `app-package.json` 版本与 `dsh-tools` 是否含 `setExecutor`。
2. **隔离启动**（不碰真实安装）：将解包目录复制为独立副本，设置独立 user-data / 独立 profile 目录（具体变量在阶段 3 首日验证），启动 0.2.2 宿主；**不修改 `D:\deepseek-harness`**。
3. **执行 04 §6 的 8 项自检**：executor 存在性、28 工具数、renderer/错误码、脚本写入拦截（修复后应为“拒绝”）、10 路由、面板 tab + SSE、CUA 工具是否出现、日志无 compatibility 拒绝。
4. **betterSidebar A/B**：先测 0.28.0（当前）；若面板不挂/报错，再在隔离 profile 中升到 0.32.1（其 peer 已指向 `^0.2.2-rc.2`），确认是 `dsh-vhcu` 还是外部插件的问题。
5. **产出**：`07-0.2.2隔离验证报告.md`（逐项 PASS/FAIL + 证据 + 结论）。

> 若阶段 3 的隔离启动成本过高，退路：只做 asar 静态核对 + 等用户真实升级后执行阶段 4；不把“模拟运行”当作验收替代。

### 阶段 4：用户真实升级（由用户执行；我们提供清单与兜底）
1. **升级前**：确认阶段 1 备份完成；记录当前版本与状态；确认 profile 无 `tools.mode` 覆盖、`tool-executor-native` 行将由 0.2.2 自带 bundle 提供。
2. **用户升级**：官方 feed 0.2.2-rc.5（已下载安装包；sha512 与 feed 一致）。
3. **升级后 smoke**：执行 04 §6 清单 + 本轮新增的拦截用例；收集 `logs`、工具注册日志、面板截图、CUA 工具列表。
4. **回滚预案**：若 P0/P1 阻断——恢复 profile 备份、安装旧版 0.2.1-rc.3（安装包/回滚包）、必要时把 VHCU junction 指回当前工作区；状态文件只回滚 settings/macros，不覆盖新产生的 session_state。
5. **产出**：`08-真实升级验证与回滚记录.md`。

### 阶段 5：发布（约 0.5 天）
1. 全量回归（Node 185 + 新增、Python 258、contract golden）。

## 8. 需要拍板的决策（按影响排序）

1. **是否现在就修 `exec.args`（P1，既有安全缺陷）？** 建议：修。它让“禁止脚本写工作区/禁止抓帧落盘”从未生效；修复是单行 + 测试。
2. **是否把 `0.2.2-rc.5` 补进 `dsh.plugin.json > compatibility.dshReleases`？** 建议：补。纯声明、零运行时风险；即使宿主不读也无害。
3. **0.2.2 的隔离验证是否执行？** 建议：执行（只解包、不安装、不碰真实目录）。否则只能等用户升级后才知道 betterSidebar/CUA 的真实表现。
4. **betterSidebar 是否升级到 0.32.1？** 建议：先测 0.28.0；只有面板运行时失败才升，避免把外部插件的变更混进本次适配。
5. **版本号定 1.1.1 还是 1.2.0？** 建议：1.1.1（兼容修复，无新能力）。
6. **CUA 共存策略**：建议默认“检测 + 提示 + 可配置互斥”，不自动禁用任何一方。
7. **`OPEN_SOURCE_RELEASE_CHECKLIST.md` 与两份 manifest 的 icon 描述矛盾**：以代码与测试为准（都有 icon），仅修文档；不改 manifest。
