## 0. 一句话结论

**0.2.2-rc.5 对 dsh-vhcu 没有 P0 阻断**：`ctx.tools.register` 的 `ToolDefinition` 契约、`ctx.on('tools/execute')`
中间件、`ctx.webServer.register(route)`、`window.__ModuleLoader__.load` 客户端模块协议、`dsh.client` 清单解析、
`engines.dsh` 兼容闸门**逐项保持兼容**（多数是逐字节相同）。

真正的变化是**架构性**的：工具执行从 `dsh-tools` 内部搬到独立的 executor 插件
（`@deepseek-ai/dsh-tool-executor-native` / `-ptc`），`ctx.tools.execute()` 从"单调用"改成"批次"，
`ToolRuntime` 类型改名为 `ToolsService`（保留 `ToolRuntime` 别名）。这些都不落在 dsh-vhcu 的使用面上，
但带来两个**部署级**前置条件，升级后必须自检（否则会从 P2 恶化成 P0）。

另发现一个**既有缺陷（非本次升级引入）**：`tools/execute` 中间的脚本写入拦截读取 `exec.args`，
而宿主契约里一直是 `exec.arguments` —— 该拦截在 0.2.1-rc.3 上**从来就没有生效过**（§7）。

### 1.3 三个必须声明的证据缺口

1. **0.2.2 安装包内层 `app.asar` 未取出**。`dsh-0.2.2-rc.5.exe` 是 NSIS/LZMA 压缩体：
   本机无 `7z`/`py7zr`，`tar` 无法解 NSIS；对 299,593,552 字节的 exe 做 8 MiB 分块扫描，
   ASCII `app.asar` 命中 **0 次**（载荷整体压缩）。因此 0.2.2 侧结论全部基于 **官方 npm 产物 + 随包 docs**，
   0.2.1 侧额外用**实机 app.asar** 交叉校验。
2. **随包 upgrade-guide 的版本标签与产物体征不符**。`docs/upgrade-guide/v0.2.1-rc.2/tool-executor-plugins/guide.md`
   描述"工具执行模式移入 executor 插件"，但 `@deepseek-ai/dsh-tool-executor-native` 在 npm 上**最早只有
   `0.2.2-alpha.2`**（`npm view ... versions`），而 0.2.1-rc.3 的 `dsh-tools` 确无 `setExecutor`
   （`021·tools/lib/index.js` 中 `setExecutor` 命中 0 次）。→ **本文一律以代码/类型实测为准，guide 只作方向性参考。**
3. **`@deepseek-ai/dsh` 的 `docs/dependency-catalog.json` 不是完整宇宙**：
   `@deepseek-ai/dsh-client-ui-slots`、`dsh-tool-executor-native/-ptc` 都不在其中，但它们确实存在于 0.2.2
   （前者 `npm pack` 成功，后者被 0.2.2 `dsh-base` 的 patch 行引用）。
   → **"catalog 里没有"不能作为"包被删除"的证据**。

## 3. 逐项契约比对

### 3.1 `@deepseek-ai/dsh-tools`：注册契约未变，执行侧被拆走

#### 3.1.1 `ToolDefinition`（确认点 1）

[021包] `021·tools/lib/types/index.d.ts:115` 与 [022包] `022·tools/lib/types/contracts.d.ts:23` 的 `ToolDefinition`
**字段集合完全一致**（`output` 必填、`execute(args, exec)`、可选 `projectContent`/`finalizeContent`/`timeoutMs`/
`isConcurrencySafe`/`presentCall`/`presentResult`），且都 `extends ToolSchema`。

`ToolSchema` 本身：[附加包] `llm-021/lib/types/types.d.ts` 与 `llm-022/.../types.d.ts` 的
`interface ToolSchema { deferLoading?; name: string; description: string; parameters: Record<string, unknown> }`
**逐字节相同**。

`register` 的实现校验也**逐行相同**：

```
021·tools/lib/index.js:2974-2983     022·tools/lib/index.js:433-442
  const name = definition.name;        const name = definition.name;
  const output = definition.output;    const output = definition.output;
  if (output === void 0 || ... typeof output.render !== "function" ...)
        throw new TypeError(`tool "${name}" must declare output { schema, render, presentationMeta? }`);
  assertSupportedJsonSchema(output.schema);

  if (name === "run_code") throw ...            // 保留名，vhcu 不撞
```

唯一差异：0.2.2 把落库值从 `definition` 改为 `{ definition, when }`，并为 `register()` 增加**可选第二参数**
`options?: ToolRegistrationOptions`（`when` 条件，`022·tools/lib/types/contracts.d.ts:110`）。
→ 只传一个参数的老写法照旧，**P3**。

**返回值/错误码**：`ToolExecutionResult` 联合体（`isError`/`error{message,info}` / `value`/`content`/`meta`）两版同形；
`ToolNotFoundError`(UNKNOWN_TOOL)、`ToolOutputError`(INVALID_TOOL_OUTPUT)、`TOOL_ABORTED(_BEFORE_DISPATCH)`
都还在（`022·tools/lib/types/contracts.d.ts:230-300`）。0.2.2 新增 `ToolContextUnavailableError`（新增型，非替换）。

#### 3.1.2 `tools/execute` 中间件（确认点 2）——**还在，签名不变**

| 版本 | 声明位置 | 签名 |
|---|---|---|
| 0.2.1 | `021·tools/lib/types/index.d.ts:58` | `'tools/execute'(this: Scoped<ToolRuntime>, exec: ToolDispatchExecution, next: () => Promise<ToolExecutionResult>)` |

## 6. 升级后的最小自检清单（只写方向，不实现）

1. **执行器存在性**：确认 profile 组合含 `tool-executor-native` 且启用；确认所有 patch 层没有
   `- id: tools { config: { mode / maxParallelSubCalls } }`。缺任一项 → 全部工具（含 28 个）不可执行。
2. **注册数量**：启动日志应有 `dsh-vhcu: registered 28 tools`（`lib/index.js:5551`）。
   `registerTools` 逐个 `try/catch` 只打日志（`:5531-5533`），任何字段不合法都只会"少几个工具"而不报错。
3. **模型可见性**：让模型调用一次 `vhcu_get_active_window` 与一个带 `output` 渲染的工具（如内存剪贴板），
   验证 `output.render` 与错误码（`E_STATE`）在新 pipeline 下仍按文本落地。
4. **中间件**：构造一次 `shell` 工具写入 `vhcu-*.py` 的调用，确认拦截是否生效——**预期仍然不生效**
   （§7 的既有缺陷），若这次要修，一并改成 `exec.arguments`。
5. **Web 路由**：`GET /vhcu/state` 返回 200；跨源带 `Origin` 返回 403；`/vhcu/frame` 返回 PNG 且带
   `x-vhcu-frame-storage: daemon-memory`（同源判定是 VHCU 自己做的，不依赖宿主）。
6. **客户端**：面板 tab 出现在 betterSidebar 中、SSE 不断流；若 tab 没出现，先看 betterSidebar 是否加载失败
   （`ctx.betterSidebar` 缺失时 VHCU 是静默 return）。

## 7. 既有缺陷（不是本次升级引入，但会干扰"升级验证"的判断）

**`exec.args` 从不存在。** 契约里 `ToolExecution`/`ToolDispatchExecution` 的解析参数叫 **`arguments`**
（0.2.1 `021·tools/lib/types/index.d.ts` 的 `ToolExecutionInput`；0.2.2 `contracts.d.ts` 同名字段），
而 dsh-vhcu 的中间件读的是 `exec?.args`：

```js
// VHCU/lib/index.js:190-194
ctx.on('tools/execute', (exec, next) => {
  const detail = detectScriptWrite(exec?.name, exec?.args);   // ← args 恒为 undefined
  if (!detail) return next();
  ...
});
```

`detectScriptWrite(name, undefined)` → `collectText(undefined)` 返回 `''` → 直接 `return null` → 恒 `next()`。
也就是说 **P9/P11 的"禁止在工区生成 vhcu-/captcha-/crop 脚本 + 禁止 Invoke-WebRequest 抓帧"从未生效过**，
在 0.2.1-rc.3 上就是如此，0.2.2 不会让它变好也不会变坏。修复方向：`exec?.arguments`；
同时给 `dev/mock-ctx.mjs` 补一个真正实现 `tools/execute` 的假 ctx（现在只认 `'dispose'`），
否则这类"静默失效"永远没有测试兜底。

## 10. 结论摘要（给 Lead 的三行版）

1. **没有 P0**：注册契约、`tools/execute` 中间件、`webServer.register`、客户端模块协议、`engines.dsh` 闸门全部兼容，
   其中多项逐字节相同；`ToolRuntime` → `ToolsService` 只是改名且保留别名。

   `maxParallelSubCalls`。当前 profile 已核查通过。
3. **两处需要人盯**：① `exec.args` 既有缺陷导致脚本写入拦截从未生效（建议本次一并修）；
   ② 0.2.2 原生 CUA 若默认启用会与 VHCU 抢输入（工具名不冲突，输入面冲突），需实机确认后再定策略。
