1. 时间 / 阶段 / 范围
====================================================================
  时间：2026-11-06 23:25 +08:00
  阶段：P23.1
  背景：
    P23 的 HITL 审批对交互任务很好，但无人值守长任务会因频繁弹窗卡死。
  目标：
    1. ⚙ 增加「自动批准破坏性宏（高危）」，默认关闭；
    2. 勾选时前端二次确认，明确数据丢失风险；
    3. 开启时 Node 跳过 requestMacroApproval，直接下发 Python；
    4. 开启时面板顶部常亮红色警告横幅；
    5. 开启时绝不卡在审批等待。

2. 本轮交付物
====================================================================
2.1 后端设置
    settings.autoApproveDestructive:
      - 默认 false；
      - mergeSettings 支持布尔热更新；
      - snapshot.settings 暴露给 UI；
      - 仅保存在插件进程内（与其他 settings 一致）。
2.2 HITL 放行
    executeStoredMacro：
      if (macro.is_destructive && !settings.autoApproveDestructive) {
         await requestMacroApproval(...);
      } else if (macro.is_destructive && settings.autoApproveDestructive) {
         note('⚠ 自动批准破坏性宏 ...（高危开关已开启）');
         // 直接进入 runInputAction → Python
      }
    - 开启时完全不创建 state.approval，不启动 120s 审批计时器；
    - 不存在等待审批的 Promise；
    - 不会因无人点击而 E_TIMEOUT/卡死。
2.3 UI 设置与二次确认
    ⚙ 新增字段：
      [自动批准破坏性宏（高危）]
    勾选时显示：
      ⚠ 高危：此操作将允许 AI 自动执行关闭、删除等操作，
      可能导致数据丢失。确认开启后请点底部「保存设置」
    按钮：[确认开启] [取消]
    - 未确认不会写入 draft.autoApproveDestructive；
    - 取消保持关闭；
    - 确认后仍需点「保存设置」；
    - 全程无 window.confirm。
2.4 红色警告横幅
    autoApproveDestructive=true 时面板顶部常亮：
      ⚠️ 自动批准破坏性宏已开启，请随时注意 AI 操作。
    CSS：红色背景 + 红色下边框 + 加粗。

4. 风险与未验证项
====================================================================
R1. 自动批准是真正的高危开关：AI 可直接关闭/删除文件或窗口；
    UI 只做一次二次确认 + 常亮横幅，运行中不再逐次拦截。
R2. 设置保存在插件进程内，DSH 重启后恢复默认关闭；
    这降低了长期误留风险，但也意味着每次无人值守前需重新开启。
R3. 自动批准路径不创建审批请求，因此不会产生/消费 state.approval；
    审计仅依赖 action 事件日志（自动批准 note）。
R4. 没有“自动批准次数上限”或“仅本次会话”附加限制；
    开关开启期间所有 destructive 宏均直接放行。
R5. 真实无人值守长任务未做端到端演练。
