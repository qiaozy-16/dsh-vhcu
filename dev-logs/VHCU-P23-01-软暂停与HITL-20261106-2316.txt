2. 本轮交付物
====================================================================
2.1 软暂停状态机
    Node state.interaction：
      {
        mode: 'running' | 'paused_by_user',
        pausedAt, resumedAt, lastUserActivityAt,
        notice: {text, at} | null
      }
    触发：
      - 视觉运行后启动独立 presence watcher（uiohook）；
      - 监听 keydown / mousedown / wheel / mousemove；
      - isAiInjecting=true 时不触发（AI 自己的注入不算用户接管）；
      - 真实用户事件 → mode='paused_by_user'；
      - clearFrameMeta()，旧截图坐标基线失效；
      - note + pushStatus，UI 蓝色横幅。
    恢复：
      - 每次真实用户事件重置 1.5s 计时器；
      - USER_TAKEOVER_RESUME_MS=1500；
      - 计时结束 → mode='running'；
      - notice='用户已停止操作，请重新截图确认状态。'；
      - note + pushStatus。
    动作门：
      - paused_by_user 时 runInputAction 不注入；
      - 返回结构化 E_PAUSED_BY_USER（非致命，不杀 daemon），
        hint 要求等待恢复并重新 vhcu_get_full_frame。
    通知模型：
      - vhcu_get_full_frame / vhcu_get_vision_events 返回
        interaction 快照（含 notice）；
      - notice 被消费后清空并 pushStatus。
    UI：
      - 蓝色横幅：
        👀 您正在接管键鼠，AI 已暂停
      - 恢复后短暂显示：
        👀 用户已停止操作，请重新截图确认状态
    录制兼容：
      - 开始宏录制前停止 presence watcher；
      - 录制期间由 recorder 回调调用 triggerUserTakeover；
      - 停止录制后重新启动 presence watcher；
      - 紧急制动停止并卸载。
    测试隔离：
      - VHCU_DISABLE_USER_TAKEOVER=1 用于自动化测试，
        避免真实桌面鼠标/键盘造成 flaky；
      - 生产默认开启。
2.2 宏 JSON：is_destructive
    - normalizeMacro 增加 is_destructive 布尔字段；
    - seedMacros 的 macro_close_active_window 默认 true；
    - 旧 macros.json 加载时自动给 close 宏补 true；
    - 自定义宏可通过：
      - 宏详情 checkbox「破坏性宏（模型执行前必须由用户审批）」；
      - 新建宏 checkbox；
      - 导入 JSON `is_destructive: true`；
      - vhcu_save_macro 参数 is_destructive。
    - list/export 保留字段。
2.3 HITL 审批状态机
    Node：
      - state.approval：{id, kind:'macro', macro, description,
        variables, requestedAt, status:'pending'}；
      - requestMacroApproval：
        - 只允许一个 pending；
        - 120s 超时 → E_TIMEOUT；
        - pushStatus（SSE status 帧）让前端弹窗；
      - executeStoredMacro：
        - destructive 宏先 await 审批；
        - 用户拒绝 → E_DENIED；
        - 用户允许 → 才进入 runInputAction → Python；
      - /vhcu/approval POST {id, decision: allow|deny}；
      - 停止视觉/紧急制动/插件清理会取消 pending。
    UI：
      - 绝对定位遮罩 + 红色弹窗；
      - 文案：
        ⚠️ 破坏性操作审批
        AI 请求执行破坏性操作（宏名），是否允许？
      - [允许] [拒绝] 按钮；
      - 无 window.confirm；
      - 审批状态由 SSE status 推送。
    SSE：
      - 使用现有 pushStatus 的 status 事件携带完整 snapshot；
      - 前端 status listener 更新 state.approval 并弹窗。

4. 风险与未验证项
====================================================================
R1. presence watcher 依赖可选 uiohook-napi；
    未安装或系统禁止全局钩子时，软暂停不可用，只记录日志。
R2. paused_by_user 期间 AI 动作返回 E_PAUSED_BY_USER（结构化软错误），
    不注入、不杀 daemon；若模型误以为可重试，需要读取 hint 重新截图。
R3. “通知模型”通过下一次 vhcu_get_full_frame / vhcu_get_vision_events
    的 interaction.notice 传递；插件无法主动向模型对话注入消息。
R4. 审批通过前 Python 未收到任何指令；审批后仍有实际注入耗时窗口。
R5. 审批请求只支持一个 pending；连续破坏性宏会串行等待。
R6. 120s 审批超时会返回 E_TIMEOUT，用户之后点击旧按钮会得到 E_STATE。
R7. 自动化测试用 VHCU_DISABLE_USER_TAKEOVER=1 隔离真实桌面输入；
    真实 uiohook 行为未在测试中验证。
R8. 用户点击审批按钮本身也会触发软暂停（真实用户输入），
    恢复后仍可继续；这是预期交互但可能让横幅闪一下。

5. 待确认决策（编号）
====================================================================
D1. 真实用户输入 → paused_by_user；AI 注入不触发。
D2. 1.5s 无输入自动恢复，notice 通过视觉工具返回。
D3. paused 期间 AI 动作软拒绝（E_PAUSED_BY_USER），不注入。
D4. 破坏性宏必须经 Node 审批状态机，拒绝 E_DENIED。
D5. 内置 macro_close_active_window 默认 destructive。
D6. 审批通过 SSE status 推送，前端本地弹窗，不使用 window.confirm。
D7. 审批超时 120s。
D8. 自动化测试禁用 presence watcher 以避免真实桌面干扰。
