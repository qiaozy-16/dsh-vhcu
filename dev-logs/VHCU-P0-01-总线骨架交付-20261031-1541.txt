0. 本轮结论（先看这 6 条）
====================================================================
C1. 总线已真实跑通：Node 守护 spawn Python daemon → READY → ping/sys.info →
    vision.start(fake) → 差分事件 → 图像面拉取 PNG → vision.stop 后零事件 →
    shutdown 无僵尸。全程 3.3s（含 4 个差分事件）。
C2. 三条车道按 D1 落地：stdio NDJSON 控制面 + loopback HTTP 图像面 + （UI 面留 P1）。
    图像面是拉模式、带 token、限流 2 并发、8 MiB 上限；模型 API 侧仍然只有 JSON。
C3. 守护层的四个真实坑已修并写进测试：Windows 被杀进程 exitCode 仍为 null（要看 signalCode）、
    重启后 seq 必须归零重建、READY 才算心跳计时起点、旧 child 的迟到 exit 必须按 child 身份忽略。
C4. Python 侧协议通道隔离（dup 真 stdout → fd1 指向 stderr）是硬前提：
    任何库的 print/traceback 都不会污染帧流。这一条没有它，总线迟早会随机错帧。
C5. 实测（fake 320x180 @8fps）：READY 348-430ms；diff P50 2.3-2.9ms；
    单帧采集 0.16-0.17ms；shutdown 445-447ms；SIGKILL 后 500ms 退避重启成功、无僵尸。
    帧图像 126B / 32x32 PNG（ROI 裁剪 + 降采样）。
C6. mss 真实抓屏未验证：本机 Python 3.13.9 未安装 mss（也没 numpy）。
    代码已做成可选依赖，缺失时返回 E_UNAVAILABLE + 可执行 hint，不会崩。

4. 六个真实踩坑（本轮实际发生并修复，建议写进团队规范）
====================================================================
K1. Windows 上被信号杀死的子进程 exitCode === null
    Node 的 child.exitCode 在 TerminateProcess/SIGKILL 后仍是 null，只有 signalCode 非空。
    只用 exitCode 判断「已退出」→ _waitForExit 会在 exit 之后继续挂 500ms 再挂 1s，
    最终误报「daemon survived SIGTERM/taskkill」且 stop() 永不 resolve。
    修复：hasExited(child) = exitCode !== null || signalCode !== null（supervisor.js:32）。

K2. 重启后 seq 从 1 开始，旧 SeqTracker 把新 READY 当 duplicate 丢掉
    表现：重启后 supervisor 永远到不了 ready，日志只有 E_SEQ duplicate seq 1。
    修复：每次 _spawn 重建 daemonSeq = new SeqTracker('daemon')。
    这条是「进程内状态」和「连接级状态」混淆，任何长连接协议都会遇到。

K3. READY 之前 lastHeartbeatAt=0，看门狗永远不触发
    表现：daemon 活着但一个心跳都不发，host 认为一切正常。
    修复：READY 时把 lastHeartbeatAt 设为当前时间（silence 从 READY 起算）。

K4. 旧 child 的迟到事件污染新 child 的状态
    kill 是异步的，退避重启可能在旧进程 exit 之前就 spawn 新进程；
    旧 stdout/exit 事件若不做身份校验，会把 this.child 置空、把新 READY 丢掉。
    修复：所有 child 事件绑定 child 形参；_onExit 首行 this.child !== child 直接忽略。
    另加 expectingExit 标记：由我们主动 kill 引发的 exit 不再计为第二次失败，
    否则熔断会在 1 次真实崩溃时被提前触发。

K5. 「ack 后再等 started 事件」会丢事件
    表现：CLI 偶发 timeout waiting for vision.started，重跑又好了。
    原因：daemon 在同一个 tick 里先 ack 再 event；await ack 恢复后监听器才挂上。
    修复：先注册监听、再发命令（cli.mjs 有注释）。凡是「命令-事件」同源协议都要这样写。

K6. shutdown 帧回 ack 时 cmdId 为空 → 自己把自己判成 E_PROTO
    协议 schema 要求 ack.cmdId ≥1；shutdown 帧没有 id。
    修复：shutdown 不 ack，直接退出（host 的 stop 本来就不等 ack）。
    教训：为「省一个字段」放宽必填，比让协议多一种合法形态更危险。

5. 已知边界（P0 明确没做，不要误以为已完成）
====================================================================
B1. mss 未验证：本机无 mss/numpy。MssSource 代码已写，但「真实抓屏 → 差分」这条链路
    需要用户在 venv 里 pip install mss 后跑 `node host/cli.mjs --source mss` 才能验收。
B2. 差分是「采样网格 + 只比较单像素」，对 1px 细线/亚像素滚动可能漏检；
    P1 再引入按 ROI 精算（或 numpy 加速）与阈值自适应。
B3. 图像面只发 PNG、不做 I/P 帧编码与增量传输；当前每次拉取都是整块 ROI。
B4. 无单实例锁：两个 host 同时跑会各自 spawn 一个 daemon（P1 接宿主时加 lockfile）。
B5. 无认证的命令来源绑定：stdio 是父子私有管道，安全边界等于「能 spawn 我的人」；
    图像面有 token，但没有速率计费/审计日志（P1 补）。
B6. 心跳/命令的时钟是墙钟（Date.now），跨休眠恢复可能出现一次误判（已有 3 次容忍）。
